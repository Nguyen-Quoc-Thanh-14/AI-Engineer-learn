# M05.03 — Đáp án bài B: định lượng lỗi N+1 qua ORM thực

**Đề B:** Lập test assert số query <=2 khi tải orders cho 100 users bằng ORM.

## Phép thử có thể chạy

[Mã SQLAlchemy ORM với SELECT counter](../MA_MAU/M05.03_bai_B_orm_query_budget.py) tạo 100 User và 200 Order trong SQLite in-memory, rồi chạy **hai cách truy vấn trên cùng dữ liệu**:

- `selectinload(User.orders)`: tải danh sách người dùng bằng 1 SELECT và orders bằng 1 SELECT; **assert ≤2 SELECT**.
- Lazy loading mặc định: 1 SELECT lấy người dùng và 100 SELECT lấy orders; **assert đúng 101 SELECT** trong fixture đã định nghĩa.

Bộ đếm gắn sự kiện SQLAlchemy `before_cursor_execute`, chỉ đếm câu SELECT, **gắn sau bước schema + seed** và được gỡ trong `finally`, tránh đếm nhầm tạo bảng, INSERT hay ảnh hưởng giữa các ca. Dữ liệu eager/lazy phải bằng nhau, mỗi user có chính xác 2 order.

**Chạy tại root repo trên môi trường có SQLAlchemy 2.x:**

```bash
python 03_HOC_PHAN/M/M05/MA_MAU/M05.03_bai_B_orm_query_budget.py
python -m unittest discover -s tests -p 'test_issue9_m0503_query_budget.py' -v
```

Bộ [kiểm thử độc lập](../../../../tests/test_issue9_m0503_query_budget.py) kiểm tra fixture 100 user, N+1 thật, các ca 1/2/10 user, dữ liệu không hợp lệ và việc tháo bộ đếm. Không sử dụng danh sách Python giả lập để khẳng định số truy vấn ORM.

## Phạm vi và giới hạn

Đây là **kết quả kỹ thuật trong SQLite, SQLAlchemy 2.x, 100 user**, không suy rộng “≤2 query” cho mọi ORM, database hoặc chiến lược eager loading. Với `selectinload`, số batch SELECT có thể tăng nếu tập user vượt ngưỡng chunking hoặc mối quan hệ phức tạp. Kiểm tra trên phiên bản DB/ORM sử dụng thực tế trước khi áp chính sách hiệu năng.
